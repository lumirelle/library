# Website Performance Optimization

## Round 1

### Question

那从用户体验看，我们应主要关注哪些阶段的耗时？fcp和lcp听了你的描述，让我感觉到它们是“浏览器”决定的，我们很难有个可量化的标准来推测，最多通过模拟访问页面来“实测”

### Answer

你的判断有一部分是对的：**FCP、LCP 的准确值需要页面实际运行后才能测得，不能只看源码就精确计算。** 但它们有明确的测量规则，也能拆解成可分析、可预算的耗时；而且测量既可以来自模拟访问，也可以来自真实用户。

我上一条把 LCP 描述为“主要内容出现”有些简化。更准确地说：**LCP 用“视口内最大的符合条件的内容元素何时显示”来近似衡量主要内容的加载速度。** 浏览器并不知道哪个元素对你的业务最重要。

**从用户体验出发，建议关注下面几件事。**

| 用户的感受 | 关注的指标 | 用途 |
|---|---|---|
| “怎么还没有内容？” | FCP | 衡量首个内容出现前的等待 |
| “我主要想看的东西出来了吗？” | LCP + 业务内容就绪时间 | 衡量核心内容到达速度 |
| “看到了，但能操作吗？” | 业务可操作时间 | 检查事件绑定、数据、初始化是否就绪 |
| “点了怎么没反应？” | INP | 衡量交互到下一次画面反馈的延迟 |
| “操作结果怎么还没出来？” | 自定义操作完成耗时 | 覆盖接口请求、计算、结果展示 |
| “页面怎么突然跳了一下？” | CLS | 衡量视觉稳定性，属于分数而非耗时 |

目前 Core Web Vitals 是 **LCP、INP、CLS**；FCP 是辅助指标。常用的“良好”目标为：

- FCP ≤ **1.8 秒**
- LCP ≤ **2.5 秒**
- INP ≤ **200 毫秒**
- CLS ≤ **0.1**

这些目标通常看真实访问的 **P75**，并区分移动端和桌面端。例如 LCP P75 ≤ 2.5 秒，意味着至少约 75% 的访问达到这个速度，而不是某次本机测试达标即可。[FCP 定义与阈值](https://web.dev/articles/fcp)、[Core Web Vitals](https://web.dev/articles/vitals)

`DOMContentLoaded`、`load` 更适合辅助诊断。用户关心的内容可能在它们之前就出现，也可能在它们之后才由接口和脚本生成。

**“由浏览器测量”不意味着“浏览器凭感觉决定”。**

FCP 的规则大致是：从导航开始，到首次绘制文本、图片等符合条件的内容。只有背景颜色发生变化，并不等于 FCP。

LCP 则会观察符合条件的图片、文本块等元素在视口中的可见大小，并更新候选。例如：

```text
0.6 秒：小标题出现       → 此时最大的候选是标题
1.0 秒：正文文本块出现   → 更大的正文成为候选
1.8 秒：首屏大图出现     → 大图成为新的候选
```

LCP 在规定的观察窗口内更新，并非永远追踪页面后续变化；用户开始点击、滚动等交互时，会停止产生新的相关候选。具体规则还包括元素类型、尺寸计算与过滤条件。[LCP 测量规则](https://web.dev/articles/lcp)

因此，确定视口和页面设计后，你通常能**预判候选元素**，例如商品主图、文章正文或横幅，再实测确认。

它也有边界：最大的宣传图不一定比旁边的“价格和购买按钮”更重要。后者需要业务指标补充。

**分析耗时时，最有用的是沿着目标内容的依赖链拆分。**

假设 LCP 元素是一张图片，典型情况可以拆成：

```text
导航开始
   │
   ├── TTFB：等待 HTML 首字节
   │
   ├── 资源加载延迟：首字节到达后，多久才开始请求主图
   │
   ├── 资源加载耗时：主图请求开始到加载完成
   │
   └── 元素渲染延迟：图片加载完后，多久才显示出来
                                                        → LCP
```

这四段分别对应不同的问题：

| 耗时较大的部分 | 优先检查 |
|---|---|
| TTFB | 重定向、连接建立、网络往返、CDN 命中、服务端处理 |
| 资源加载延迟 | 图片是否要等 JS、接口或 CSS 才能被发现，是否被错误地懒加载，调度优先级 |
| 资源加载耗时 | 图片字节量、连接与带宽、CDN、缓存 |
| 元素渲染延迟 | 阻塞渲染的 CSS、主线程长任务、图片解码、隐藏状态、布局和绘制 |

TTFB 包含客户端到收到首字节之前的等待，**不能直接当作后端处理时间**。后端处理只是其中一部分。上面的图片拆分适用于常见加载路径；预加载等情况需要按实际时间线归因。[LCP 耗时拆解](https://web.dev/articles/optimize-lcp)

**可以推测性能，但要推测“关键路径”，不能把所有资源耗时相加。**

考虑一个简化的依赖图：

```text
HTML 首字节：0.4s
        │
        ├── CSS 就绪：0.8s ──────────────────┐
        │                                    │
        └── JS 就绪并执行：1.0s               │
                    ↓                        │
               接口完成：1.5s                │
                    ↓                        │
               主图完成：1.9s ───────────────┤
                                             ↓
                                      显示主图：2.0s
```

这里可以提前判断：

- CSS 和 JS 部分并行，不能简单相加。
- 主图被藏在“JS → 接口 → 图片”这条串行链后面。
- CSS 从 0.8 秒优化到 0.6 秒，可能改善 FCP，却未必改善主图的 LCP。
- 如果能让 HTML 直接提供主图地址，就有机会让图片更早开始下载。

概念上可以写成：

```text
目标元素显示时间
≈ max(相关内容就绪时间, 样式就绪时间, 必需脚本工作完成时间)
  + 剩余渲染与呈现时间
```

这是用于分析的模型，实际还存在资源竞争和调度影响。它能帮助你定位瓶颈、制定预算；设备速度、网络状况、缓存状态等最终仍需运行数据校准。

**交互阶段也要区分“立即反馈”和“业务完成”。**

例如点击“搜索”：

```text
点击
 ↓ 等待主线程
执行事件处理代码
 ↓
显示“正在搜索”                 ← 这次交互的下一帧反馈
 ↓
接口返回
 ↓
显示搜索结果                   ← 业务完成
```

INP 关注交互到下一次画面呈现之间的延迟，覆盖输入等待、事件处理和呈现延迟。它通常不包含之后整段异步接口等待，因此一个页面可以 INP 很好，但搜索结果仍然要等数秒。

这时应另外记录“点击搜索 → 结果展示”的耗时。[INP 定义](https://web.dev/articles/inp)

**测量上，应该同时建立两种反馈。**

| 方式 | 怎么做 | 主要回答什么问题 |
|---|---|---|
| 实验室测试 | 固定设备、网络、视口和缓存条件，用 DevTools、Lighthouse 或自动化浏览器重复测试 | 为什么慢？这次修改有没有改善？ |
| 真实用户监测 RUM | 页面运行时采集性能指标，并按页面、设备、地区等聚合 | 用户实际有多慢？哪些群体受影响？ |

真实用户监测不需要人工逐个打开页面。例如 Google 的 `web-vitals` 库可以从浏览器性能 API 收集数据：

```js
import { onFCP, onLCP, onINP, onCLS } from "web-vitals";

onFCP(reportMetric);
onLCP(reportMetric);
onINP(reportMetric);
onCLS(reportMetric);
```

`reportMetric` 由你的监控系统实现，用于上报和聚合。这类库还处理部分页面生命周期细节，通常比直接读取一次性能条目更可靠。[web-vitals 官方实现](https://github.com/GoogleChrome/web-vitals)

对于业务指标，你可以明确定义：

- 商品页：商品名称、价格和主图就绪，购买按钮完成初始化。
- 报表页：首屏数据已展示，筛选控件可操作。
- 搜索页：从提交查询，到对应结果完成更新。

然后用 `performance.mark()`、`performance.measure()` 记录里程碑。需要明确埋点测的是“数据返回”“DOM 已提交”还是更接近“画面已呈现”的时刻；框架更新完成回调并不自动证明像素已经显示。[User Timing API](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/User_timing)

实际做项目时，我会把 **LCP、INP、CLS，以及一个明确的业务就绪指标**放到主要看板上；用 FCP、TTFB、资源时间线和主线程记录解释原因。制定预算时围绕关键依赖链，验收时同时看固定条件下的测试结果和真实用户的 P75，并关注较慢用户的 P95。

## Round 2

### Question

1. 我该如何正确测量一个网页的性能，比如：使用pagespeed还是浏览器内置的lighthouse？是否需要使用浏览器内置的performance工具？或者说主流团队在用其他的监测工具？
2. 它们各自怎么使用，比如获得了结果后我应该看什么，即怎么看这些指标和这些指标意味着什么？有什么注意事项？

### Answer

建议你采用这套组合：**用 PageSpeed Insights 了解线上状况，用 Lighthouse 建立可重复的基线，用 Performance + Network 定位原因；上线后用真实用户监测验证效果。**

这些工具回答的是不同问题。对于开发者，Performance 面板值得掌握，但一开始只需要会看几个关键区域。

| 工具 | 主要用途 | 数据来自哪里 |
|---|---|---|
| PageSpeed Insights，简称 PSI | 快速检查公开网页、查看真实用户体验 | CrUX 历史数据 + 云端 Lighthouse 测试 |
| 浏览器 Lighthouse | 测试本地、测试环境、登录后的页面，比较修改前后 | 当前机器执行的实验室测试 |
| Performance 面板 | 定位脚本、布局、绘制、交互中的瓶颈 | 当前访问的性能记录 |
| Network 面板 | 分析请求时机、依赖、缓存和网络耗时 | 当前访问的网络记录 |
| RUM，例如 Sentry、Datadog 或自建采集 | 持续观察真实用户，按版本、地区、设备分析 | 接入监控的真实访问 |
| Lighthouse CI | 在构建流程中发现性能退化 | 固定环境下的自动化测试 |

下面按实际操作顺序讲。

**开始之前，先明确“要测的场景”，否则结果难以比较。**

同一 URL 在不同状态下，可能相当于不同的页面。建议至少固定：

- **页面版本**：使用生产构建，避免开发模式、热更新等干扰。
- **用户状态**：是否登录、展示哪些数据、是否出现同意弹窗。
- **设备与视口**：桌面还是手机，窗口大小是否相同。
- **网络与 CPU 条件**：是否限速、限速配置是什么。
- **缓存状态**：首次访问与重复访问分开测。
- **操作场景**：首次打开、切换路由、搜索、展开复杂组件等分别测试。

我建议修改前后各测 **3～5 次**，记录具体指标的中位数和波动范围。这是日常对比的起点，不是统计上充分的真实用户样本。

使用没有扩展的测试配置文件，关闭高负载后台程序，保持页面前台运行。手机模拟模式主要改变视口等环境；CPU 降速也不能完全复现真机，重要的移动端流程还应在代表性手机上验证。

还有一个容易混淆的地方：**禁用 HTTP 缓存，不等于清除了 Service Worker、Cache Storage、DNS 缓存或已有连接。** 记录你实际采用的设置，比笼统写“冷启动测试”更可靠。

**使用 PageSpeed Insights 时，要把报告中的两套数据分开读。**

打开 [PageSpeed Insights](https://pagespeed.web.dev/)，输入公开可访问的 URL，分别查看移动端和桌面端。

报告通常包含：

| 部分 | 含义 | 适合回答的问题 |
|---|---|---|
| 真实用户体验 | CrUX 最近 28 天的滚动统计 | 用户最近实际体验如何？ |
| 性能问题诊断 | 刚刚执行的一次 Lighthouse 测试 | 在这次测试条件下，哪里可能有问题？ |

读真实用户部分时，先确认：

1. 当前展示的是**该 URL**，还是整个 **Origin**，例如 `https://example.com`。
2. 当前是移动端还是桌面端。
3. LCP、INP、CLS 的 P75，以及良好、待改善、差的访问占比。

某个页面样本不足时，报告可能展示 Origin 数据；也可能没有真实用户数据。**没有数据不代表性能良好。**

这部分来自符合采集条件的 Chrome 用户，并不是你所有用户的完整记录。历史窗口也意味着，今天上线的优化不会立即完全体现在这里。[PSI 官方说明](https://developers.google.com/speed/docs/insights/v5/about)

读下面的实验室部分时，先看具体指标、页面截图与测试环境，再看总分。

例如：

```text
真实用户 LCP P75：2.1 秒
本次实验室 LCP：4.0 秒
```

这两个结果可以同时正确：真实用户与测试机器的地区、设备、网络、缓存和页面内容可能不同。用真实用户数据确定影响范围，用实验室测试复现和排查。[实验室与真实用户数据的差异](https://web.dev/articles/lab-and-field-data-differences)

**使用浏览器 Lighthouse 时，重点是建立固定的比较条件。**

基本步骤：

1. 打开待测页面和 DevTools，进入 **Lighthouse**。
2. 选择 **Navigation**，测一次完整页面加载。
3. 选择 **Mobile** 或 **Desktop**，勾选 **Performance**。
4. 检查存储清理、限速等设置。
5. 运行审计，保存报告，重复测试。

登录页面尤其要检查存储设置，避免清理后实际测成登录页。每次看一下报告截图，确认测到的是预期页面。

Lighthouse 默认通常使用**模拟限速**：基于采集到的加载数据，推算指定网络和 CPU 条件下的指标。因此，报告指标不一定与原始 trace 的时间完全一致。浏览器版本、Lighthouse 版本、测试设置和执行机器也会影响结果。[DevTools Lighthouse 使用说明](https://developer.chrome.com/docs/devtools/lighthouse/)

**报告里，优先读具体指标，再判断该往哪里查。**

| 指标 | 怎么理解 | 偏高时先查什么 |
|---|---|---|
| TTFB | 从导航开始到收到 HTML 首字节的等待 | 重定向、连接、网络、CDN、服务端 |
| FCP | 首个符合条件的内容出现时间 | HTML 响应、阻塞 CSS、字体、早期脚本 |
| LCP | 最大内容元素的显示时间 | 目标元素、资源发现时机、下载、显示前的阻塞 |
| TBT | 测量窗口中，长任务超过 50ms 部分的累计时长 | 主线程上的 JS、布局等重任务 |
| CLS | 非预期布局移动的程度 | 图片占位、广告、字体替换、动态插入内容 |
| Speed Index | 页面可见内容逐步显示的整体速度 | 配合截图序列看显示过程 |

常用真实用户目标仍是：FCP ≤ 1.8 秒、LCP ≤ 2.5 秒、INP ≤ 200ms、CLS ≤ 0.1。TTFB 的常用参考目标为 ≤ 800ms，但它是诊断指标，包含网络等开销，不能直接当作后端耗时。[指标阈值](https://developers.google.com/speed/docs/insights/v5/about)

TBT 值得单独说明。例如测量窗口中有两个任务：

```text
任务 A：120ms → 计入阻塞时间 70ms
任务 B： 80ms → 计入阻塞时间 30ms

TBT = 100ms
```

普通 Lighthouse 加载审计并没有执行真实用户的完整交互，**TBT 不能替代 INP**。TBT 很低的页面，也可能在点击某个按钮时突然执行大量代码。[TBT 定义](https://developer.chrome.com/docs/lighthouse/performance/lighthouse-total-blocking-time)

Lighthouse 总分是多个指标经过转换、加权后的结果，**不是“用户满意度百分比”**。性能建议也不是每一项直接扣分；最终改善多少，要看修改有没有改善实际指标。[Lighthouse 评分机制](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring)

所以看到“减少未使用的 JavaScript”“预计节省 300ms”时，应把它当作调查线索。多个建议可能重叠，预计节省时间不能直接相加。

**需要解释“为什么慢”时，就进入 Performance 面板。**

加载和交互，最好分别录制。

测加载：

1. 打开 **Performance**，设置固定的网络、CPU 和缓存条件。
2. 开启截图采集。
3. 点击“重新加载并录制”。
4. 保留覆盖首屏加载的记录。

测交互：

1. 页面进入待测状态。
2. 点击录制。
3. 执行一个明确操作，例如输入搜索词、切换筛选项。
4. 等画面反馈或结果出现后停止。

现代 Performance 面板也能在实时视图显示本地 LCP、CLS，以及交互后得到的 INP。这里反映的是你当前设备和当前访问，不是线上用户的分布。[Performance 面板概览](https://developer.chrome.com/docs/devtools/performance/overview)

**读 trace 时，建议按“现象 → 时间点 → 相关工作”的顺序。**

先看截图序列：白屏到什么时候？标题何时出现？主图何时出现？内容有没有移动？

随后只研究对应时间段，重点看这些区域：

| 区域 | 重点看什么 |
|---|---|
| Insights | LCP 分段、请求发现、阻塞资源、强制布局等提示 |
| Timings / 指标标记 | FCP、LCP 等发生在哪个时刻 |
| Network | 关键资源何时开始、何时结束、依赖谁 |
| Main | 主线程被哪些脚本、样式、布局、绘制任务占用 |
| Interactions | 慢交互的输入等待、处理和呈现阶段 |
| Layout shifts | 哪个时间点发生移动、涉及哪些元素 |

Insights 可以先帮你缩小范围，包括 LCP breakdown、LCP request discovery、Forced reflow、Layout shift culprits 等。[Performance Insights](https://developer.chrome.com/docs/performance/insights)

再读主线程火焰图：

- 横轴是时间，块越宽，持续越久。
- 纵向嵌套表示调用或工作之间的包含关系。
- **Self time** 是自身耗时，**Total time** 包括子调用；父子耗时不要重复相加。
- **Bottom-up** 适合找选定时间段里累计耗时较多的函数。
- **Call tree** 适合追踪是谁调用了它。

先框选慢的那几百毫秒，再看这些统计，比直接分析整段十几秒记录容易得多。[Performance 记录分析](https://developer.chrome.com/docs/devtools/performance/reference)

录制本身有开销。高级绘制检测、CSS 选择器统计等额外选项可能显著影响性能，常规基线测试不要随意开启；诊断时再按需使用。

**Network 面板用来把“网络慢”进一步拆开。**

找到 HTML 或 LCP 对应资源，点击请求，查看：

| 位置 | 应该看什么 |
|---|---|
| Timing | 排队、DNS、连接、TLS、等待首字节、内容下载分别耗时多少 |
| Initiator | 请求由 HTML、CSS 还是哪段 JavaScript 触发 |
| Headers | 缓存策略、内容编码、响应状态等 |
| Size / Transferred | 实际传输量、资源大小，以及是否来自缓存 |
| Waterfall | 请求何时开始，是否形成串行依赖 |

例如，一张主图在导航后 **2 秒才开始请求，200ms 就下载完**，优先调查的是“为什么发现或启动这么晚”，单纯继续压缩图片可能收益很小。

Timing 中的“Waiting for server response”也包含网络往返等因素；需要结合服务端 tracing 或 `Server-Timing` 才能进一步确认后端处理成本。[Network 面板参考](https://developer.chrome.com/docs/devtools/network/reference)

**可以用下面几种结果组合来练习判断。**

| 观察到的结果 | 合理的下一步 |
|---|---|
| TTFB 高，FCP 和 LCP 都随之偏晚 | 检查文档请求路径、CDN、连接与服务端 |
| FCP 很快，LCP 很慢 | 确认 LCP 元素，检查资源发现、下载、晚到的数据 |
| 图片早已下载完，LCP 仍然很晚 | 查阻塞 CSS、主线程任务、隐藏状态和渲染工作 |
| TBT 高 | 在对应时间段查长任务及调用栈 |
| TBT 低，但真实用户 INP 高 | 录制实际慢操作，尤其是加载后才执行的处理逻辑 |
| 加载测试 CLS 很低，线上 CLS 高 | 测滚动、懒加载、广告刷新和延迟内容 |
| 所有加载指标都好，但用户仍抱怨慢 | 测业务数据就绪和操作结果展示时间 |

这些是排查方向，需要用请求和 trace 验证原因。

比如 LCP 分段是：

```text
TTFB                 0.5 秒
资源加载延迟          1.8 秒
资源加载耗时          0.3 秒
元素渲染延迟          0.2 秒
--------------------------------
LCP                  2.8 秒
```

你应优先调查那 **1.8 秒**的依赖链，而不是看到大图就先压缩。Performance 的 LCP breakdown 正是为这种判断提供依据。[LCP 分段说明](https://developer.chrome.com/docs/performance/insights/lcp-breakdown)

**团队持续监测时，通常会把本地诊断、自动化测试和 RUM 配合起来。**

你不需要一开始购买多套产品，可以逐步建立：

| 环节 | 怎么使用 | 获得结果后看什么 |
|---|---|---|
| 日常开发 | Lighthouse 建基线，Performance 定位 | 具体指标是否变化，瓶颈是否消失 |
| 合并或发布前 | Lighthouse CI 测代表性页面，设置预算 | 同环境下有无明显退化、资源体积是否超预算 |
| 发布后 | RUM 采集真实访问，附带版本、路由等信息 | 同类用户的 P75/P95、差体验占比、样本量 |
| 定期检查 | PSI 查看公开页面及 CrUX 趋势 | 长期体验是否改善，移动端是否落后 |

[Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/getting-started.md) 可以自动运行审计并检查预算。线上 RUM 可以选择 [Sentry](https://sentry.io/for/web-vitals/)、[Datadog](https://docs.datadoghq.com/real_user_monitoring/application_monitoring/browser/monitoring_page_performance/)，也可以用 [`web-vitals`](https://github.com/GoogleChrome/web-vitals) 接入自己的数据平台。选择哪套，通常取决于已有监控、归因能力和成本。

RUM 看板不要只放全站平均值。建议按页面类型、设备、地区、版本分组，结合样本量查看 P75、P95 和差体验比例。不同 SDK 对 SPA 路由切换、指标生命周期的处理可能不同，比较前要核对口径；没有采集到 INP 也可能只是用户没有发生符合条件的交互，不能记为零耗时。

你第一次实操时，可以只做一个明确任务：**选一个代表性页面，固定条件跑 5 次 Lighthouse，找到最突出的指标，用一段 Performance 记录解释它，再修改一个原因并用相同条件复测。** 记录“指标 → 证据 → 修改 → 复测结果”，比单独保存一个总分更有价值。
